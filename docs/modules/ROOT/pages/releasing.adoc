= Releasing

include::./includes/attributes.adoc[]

The build publishes eleven artifacts under `org.sitenetsoft`, all at the same version. Four modules set
`maven.deploy.skip` and stay unpublished:

* `quarkus-topaz-grpc-generator`, the proto generation application behind `bin/generate.sh`.
* `quarkus-topaz-integration-tests`.
* `quarkus-topaz-security-no-rest-tests`.
* `quarkus-topaz-docs`.

[cols="2,1,3"]
|===
| Coordinates | Packaging | Contents

| `quarkus-topaz-parent`
| pom
| Parent of every module.

| `quarkus-topaz-grpc-parent`
| pom
| Parent of the generated stubs.

| `quarkus-topaz-grpc`
| jar
| The generated gRPC stubs. The client runtime depends on it.

| `quarkus-topaz`
| jar
| Client runtime. Applications declare this one. See xref:index.adoc[Quarkus Topaz].

| `quarkus-topaz-deployment`
| jar
| Build-time augmentation for the client. Quarkus resolves it from the descriptor of the runtime jar. Applications
never declare it.

| `quarkus-topaz-security-parent`
| pom
| Parent of the security extension.

| `quarkus-topaz-security`
| jar
| Route policy and interceptors. See xref:security.adoc[Security].

| `quarkus-topaz-security-deployment`
| jar
| Build-time augmentation for the security extension. Applications never declare it.

| `quarkus-topaz-zanzibar-parent`
| pom
| Parent of the Zanzibar connector.

| `quarkus-topaz-zanzibar`
| jar
| The quarkus-zanzibar connector. See xref:zanzibar-connector.adoc[Zanzibar connector].

| `quarkus-topaz-zanzibar-deployment`
| jar
| Build-time augmentation for the connector. Applications never declare it.
|===

IMPORTANT: The artifact ids must stay exactly as above. The `META-INF/quarkus-extension.properties` file of each
runtime jar names its deployment artifact. Quarkus resolves the deployment module from it at augmentation time. If
you rename only one module of a pair, every consumer breaks at build time, not at runtime.

== The release workflow

`.github/workflows/release.yml` publishes to the https://central.sonatype.com[Central Portal]. It runs when you push
a `v*` tag. You can also dispatch it by hand, from `master` only. The workflow runs one release at a time, so two tags
pushed close together do not race into the Portal.

. `bin/release-check.sh` refuses a `-SNAPSHOT` version and a tag that does not match the POM version. It also
refuses a README that still advertises a snapshot or says that nothing is published yet. It prints the version it
found, and the later steps reuse that version.

. It runs `mvn -T 4 verify`, the full build and the integration tests. It does not rebuild the native image. A tag
points at a commit that already went through `ci.yml` on `master`.

. It imports the signing key. It fails at once if `SIGNING_KEY` is not set, since Central rejects unsigned artifacts.

. It runs `mvn -Prelease deploy` into a file repository at `target/staging-deploy`. This deploy signs every jar and
POM and attaches the sources and Javadoc jars.

. It deletes the `maven-metadata.xml*` files. The file-repository deploy always writes them, but a Portal bundle
must not contain them.

. It runs `bin/check-staging.sh target/staging-deploy`, which rejects metadata files. The check verifies that
exactly the eleven artifacts above are present at one version. Each artifact needs its POM, its jars and a signature
for every file. The upload endpoint accepts an unsigned or partial bundle that fails only minutes later. The check
fails early instead, while the log still says why.

. It zips the staging directory to `target/central-bundle.zip` and uploads the zip to the Portal. The workflow keeps
the zip as a workflow artifact for 30 days.

. It polls the Portal until the deployment is `VALIDATED`, `PUBLISHED` or `FAILED`. It fails on `FAILED` or after
ten minutes.

. On a tag, it creates the GitHub release with generated notes. The release is a draft unless the deployment is
already `PUBLISHED`.

=== Setting the version

The version lives in the POMs. With `-Pdocs`, the Maven plugin updates the docs module too. Set the version, replace
the pre-release text in the README and run the preflight locally. Then commit, tag and push:

[source,bash]
----
mvn -Pdocs org.codehaus.mojo:versions-maven-plugin:2.18.0:set -DnewVersion=0.1.0 -DgenerateBackupPoms=false
sed -i 's/0.1.0-SNAPSHOT/0.1.0/g' README.md
sed -i 's/^:project-version:.*/:project-version: 0.1.0/' docs/modules/ROOT/pages/includes/attributes.adoc
bin/release-check.sh v0.1.0
git commit -am "Release 0.1.0" && git tag v0.1.0 && git push origin master v0.1.0
----

The first `sed` replaces all four coordinates in the README. The second sets the `{project-version}` attribute in
`docs/modules/ROOT/pages/includes/attributes.adoc`. These pages use that attribute, and `versions:set` does not touch
it. Also drop the sentence "Status: pre-release, nothing is published yet." from the first paragraph by hand.
`bin/release-check.sh` fails while any of these still says `-SNAPSHOT`. It also fails on any `pom.xml` that still
declares a snapshot version.

Then move `master` on to the next development version with the same command and push:

[source,bash]
----
mvn -Pdocs org.codehaus.mojo:versions-maven-plugin:2.18.0:set -DnewVersion=0.2.0-SNAPSHOT -DgenerateBackupPoms=false
git commit -am "Start 0.2.0-SNAPSHOT" && git push origin master
----

In this bump, `attributes.adoc` stays at the released version. The docs on `master` then show what users can
download.

=== Secrets it needs

[cols="1,2"]
|===
| Secret | Purpose

| `SIGNING_KEY`
| ASCII-armoured private PGP key: `gpg --armor --export-secret-keys KEY_ID`. Its public half must be on a key server,
such as `keyserver.ubuntu.com` or `keys.openpgp.org`. Otherwise Central rejects the signatures.

| `SIGNING_PASSWORD`
| The key's passphrase. The workflow hands it to the GPG plugin as `MAVEN_GPG_PASSPHRASE`, with loopback pinentry.

| `CENTRAL_USERNAME`, `CENTRAL_PASSWORD`
| A Central Portal user token, not the account password. Generate it on the Portal under View Account -> Generate
User Token. The account of the token must have the `org.sitenetsoft` namespace verified on the Portal.
|===

Nothing in the build stores credentials. Local builds need none. Signing and the sources and Javadoc jars belong to
the `release` profile, which is off by default.

=== Publishing type

A tag push uploads with `publishingType=USER_MANAGED`. The deployment stops at *validated*. Nothing reaches Central
until someone presses *Publish* at https://central.sonatype.com/publishing/deployments.

The workflow marks this with a warning and creates the GitHub release as a *draft*. The tag then never advertises
artifacts that users cannot download. Publish the draft after you release the deployment. A manual dispatch can
choose `AUTOMATIC`, which releases at once and cannot be undone.

== Checking before you publish

[source,bash]
----
mvn -T 4 install -DskipTests
----

This writes the artifacts to `~/.m2/repository/org/sitenetsoft/`. Then build a sample application against the local
repository. Declare only `org.sitenetsoft:quarkus-topaz:{project-version}`, plus the security or Zanzibar artifacts
if you use them. Confirm that the extensions resolve and augment. This check catches a wrong artifact id or
descriptor before a consumer does.

To inspect the exact bundle that the workflow would upload, repeat its steps with signing off. You need no key and no
credentials:

[source,bash]
----
mvn -T 4 -DskipTests -Prelease -Dgpg.skip deploy "-DaltDeploymentRepository=staging::file://$PWD/target/staging-deploy"
find target/staging-deploy -name 'maven-metadata.xml*' -delete
bin/check-staging.sh target/staging-deploy --unsigned
----

The commands delete the metadata files first, for the same reason as in the workflow. The file-repository deploy
always writes them, and the check rejects them. On a `-SNAPSHOT` version, the staged files carry timestamped names,
which the check accepts. `--unsigned` skips the signature requirement and nothing else.
