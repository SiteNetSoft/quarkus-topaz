= Client

== Beans

The extension produces three `@Singleton` beans that share two gRPC channels, one to the authorizer and one
to the directory:

[source,java]
----
@Inject TopazClient topaz;           // authorizer(), directory(), blocking()
@Inject AuthorizerClient authorizer; // the same instance as topaz.authorizer()
@Inject DirectoryClient directory;   // the same instance as topaz.directory()
----

The channels are Vert.x gRPC client channels on the Quarkus event loop. Generated stubs keep their proto packages
(`aserto.authorizer.v2`, `aserto.directory.reader.v3`, ...) and come from the `quarkus-topaz-grpc` artifact.

== API

All methods return Mutiny types. Each client also exposes its raw Mutiny stubs for requests the convenience
methods do not cover.

[cols="1,3"]
|===
|Method |Purpose

2+h|`AuthorizerClient`
|`isAllowed(identity, policyPath, decision, resource)` |One decision as `Uni<Boolean>`; see <<is-allowed>>.
|`is(identity, policyPath, decisions, resource)` / `is(IsRequest)` |Several decisions as an `IsResponse`.
|`decisionTree(...)`, `query(...)`, `compile(...)` |The other authorizer calls.
|`listPolicies()`, `getPolicy(id)` |The loaded policy modules.
|`info()` |Topaz version information.
|`stub()` |The raw `MutinyAuthorizerStub`.

2+h|`DirectoryClient`
|`check(objectType, objectId, relation, subjectType, subjectId)` |Whether the subject has the relation or
permission on the object.
|`checks(List<CheckRequest>)` |Several checks in one call; results in request order.
|`getObject`, `setObject`, `deleteObject` |Objects.
|`getRelation`, `setRelation`, `deleteRelation` |Relations.
|`getManifest()`, `setManifest(yaml)`, `deleteManifest()` |The directory manifest as YAML; chunking is handled
for you.
|`importData(Multi<ImportRequest>)` |Streams an import and returns an `ImportSummary` of counts and errors.
|`export(ExportRequest)` |Streams the directory contents.
|`reader()`, `writer()`, `model()`, `importer()`, `exporter()` |The raw Mutiny stubs.
|===

== Identity contexts

`IdentityContexts` builds the `IdentityContext` passed to authorizer calls:

[cols="1,3"]
|===
|Factory |Caller

|`none()` |Anonymous.
|`subject(String)` |A subject (user key, email, ...) that Topaz resolves through the directory.
|`jwt(String)` |A JWT whose `sub` claim Topaz resolves through the directory. Topaz does not validate the token.
|`manual(String)` |An identity passed to the policy as is, without directory resolution.
|===

For `subject` and `jwt`, the identity must exist in the directory as an `identity` object with an `identifier`
relation to a `user`; otherwise Topaz answers `NOT_FOUND` (error `E30017`). The quick start's manifest and data show
that shape.

Topaz does not validate the token passed to `jwt(...)`: it does not check the signature, it parses the token and
resolves its `sub` claim through the directory. Authenticate the request in your application (e.g. quarkus-oidc)
before forwarding the token; pass the raw token only so Topaz can read its subject.

[[is-allowed]]
== `isAllowed` fails closed

`isAllowed` asks for one named decision and returns `true` only when the response contains that decision with value
`true`. A decision the policy does not produce is `false`.

Errors are never turned into a boolean. A gRPC failure, an unknown policy path (Topaz answers `INVALID_ARGUMENT`), an
unresolvable identity or an expired deadline fails the `Uni` with `io.grpc.StatusRuntimeException`. Handle it where
the decision is enforced, for example by answering 403:

[source,java]
----
return topaz.authorizer().isAllowed(subject(user), policy, "allowed", Map.of("id", id))
        .onFailure(StatusRuntimeException.class).recoverWithItem(false);
----

== Deadlines

`quarkus.topaz.deadline`, or `quarkus.topaz.authorizer.deadline` / `quarkus.topaz.directory.deadline`, sets a
per-call deadline. It starts when a `Uni` or `Multi` is subscribed to, so each retry gets a fresh deadline, and it
applies to streaming calls (manifest, import, export) too, where it bounds the wait for the first item. The client
enforces the deadline itself: a call against a server that accepts the connection and never answers fails with
`DEADLINE_EXCEEDED` once the deadline elapses. A refused connection fails immediately with `UNAVAILABLE`, deadline
or not. Without a deadline, calls have no time limit, except that the health check and the Dev UI give up after 10
seconds.

== Connection security

`quarkus.topaz.plain-text=true` gives plaintext channels and wins over any TLS configuration. Otherwise TLS is
configured per service through `quarkus.topaz.authorizer.tls-configuration-name` or
`quarkus.topaz.directory.tls-configuration-name`, falling back to `quarkus.topaz.tls-configuration-name`, each
naming a configuration of the Quarkus TLS registry. With no name set, the registry's default TLS configuration is
used when it defines a trust store or trust-all; otherwise the channel is plaintext. `plain-text=false` requires
TLS: with no named configuration and no usable registry default, the channel uses TLS with the JVM default trust
store; it never falls back to plaintext. A TLS configuration name the registry does not know fails startup.

`quarkus.topaz.api-key` (or the per-service `api-key`) is sent as `authorization: basic <key>` on every call.
`quarkus.topaz.tenant-id` adds an `aserto-tenant-id` header for legacy Aserto deployments; Topaz ignores it.

== Blocking facade

`topaz.blocking()` exposes `authorizer()` and `directory()` with the same methods returning plain values. It shares
the channels of the reactive client. Each call waits at most the configured deadline plus one second (so the gRPC
deadline fires first), or 30 seconds without one. Failures, including an exceeded wait, are thrown as
`io.grpc.StatusRuntimeException` (`DEADLINE_EXCEEDED` for a timeout).
Call it from worker threads only, never from the event loop.

[source,java]
----
boolean allowed = topaz.blocking().authorizer()
        .isAllowed(IdentityContexts.subject("rick@the-citadel.com"), "todoApp.DELETE.todos.__id", "allowed",
                Map.of("id", "todo-1"));
----

== Building a client outside CDI

`TopazClient.builder()` works without a running Quarkus application, for example in a test JVM seeding data into a
native binary or to reach a second Topaz:

[source,java]
----
try (TopazClient client = TopazClient.builder()
        .authorizer("localhost", 8282)
        .directory("localhost", 9292)
        .plainText(true)
        .apiKey("...")      // optional
        .build()) {
    boolean owner = client.blocking().directory().check("todo", "todo-1", "owner", "user", "rick@the-citadel.com");
}
----

The builder also takes `tenantId`, `deadline`, `tlsConfiguration`, extra `interceptors`, an existing `vertx`, or
ready-made `authorizerChannel` / `directoryChannel`. Without a `vertx`, the client creates its own Vert.x instance.
`close()` closes the channels and the Vert.x instance it created, never ones that were passed in.
